# Current Slice: dynamic social-media preview image for the feed

### Target

A [social media preview image](https://support.metropublisher.com/hc/en-us/articles/31523564070420-Preview-Image-Settings-for-Social-Media) for `bobby.houseofmoran.io` which can be shown on facebook, twitter etc.

* This should be calculated dynamically based on the same `quality-7d` content, and cached using the same last-modified caching from elsewhere.
* We can use something like the layout algorithms used in [linzer](https://github.com/mikemoraned/geo/blob/main/apps/linzer/backend/layout/src/bin/layout.rs) e.g. `Guillotine` from the `binpack2d` crate.
* We shouldn't use the full feed content for this but instead select the first 9 or 10 best and then in the created image put a fade effect on the bottom. This way we get a nice legible image which gives a taste of the content but doesn't take an algorithmically long time to layout.

This is a genuine server-side image-composition feature (compose a montage, render it, wire up the OG/Twitter meta tags, cache it), which is why it's its own slice rather than part of the 1.0 feed polish.

### Decisions

* **Composed in `skeet-feed`, on demand, served at a new route** (working name `GET /preview.png`). No new stored artifact and the publisher is untouched — chosen over publisher-precompute to keep it dynamic and the data flow simple. The web app gains an outbound image-fetch + decode/compose path it didn't have before (today it only renders HTML and references CDN thumbnails by URL).
* **Content = the served/fallback-resolved list**, read through the existing `PublishedImagesSource::published_images()` — the *same* list `home()` renders (`quality-7d` normally, widening to e.g. `quality-4w` when degraded), so the preview matches what a visitor actually sees. The published order is already best-first, so take the first 9–10.
* **Only live tiles.** Apply the same `is_live` filter the grid uses (`image_url_exists && skeet_id_exists`) *before* picking the 9–10, so the montage can never show a dead thumbnail. (The list is a superset for appraise; the preview renders the same subset the grid does.)
* **Pixels come from the Bluesky CDN thumbnail URLs** already on each `PublishedImage` (`image_url`) — the feed downloads them (it has no store access). `reqwest` is already a `skeet-feed` dependency.
* **Fetched tiles are cached with `moka`.** A bounded `moka::future::Cache<ImageUrl, DynamicImage>` (async concurrent cache, TinyLFU eviction — LRU-family) keyed by thumbnail URL, holding the **decoded** image so repeat renders skip both the download *and* the decode. Between content changes the served list shifts by only a few items, so most of the ~10 tiles are cache hits across regenerations. Chosen over an HTTP-response-layer cache (`http-cache-reqwest`) because caching the decode is the bigger win and the CDN cache-semantics that layer honours are largely redundant with our own content-signature invalidation. New dep: `moka` (async feature).
* **Output: 1200×630 PNG** — the standard Open Graph / Twitter `summary_large_image` size (1.91:1), which unfurls large on Facebook/X/LinkedIn/Slack. PNG keeps the montage edges crisp.
* **Layout: shelf rows** — every tile scaled to a common column width (~`canvas/4`, aspect preserved), laid out `MONTAGE_COLUMNS` per row with each row as tall as its tallest tile, plus a **fade at the bottom** so it reads as a legible "taste" of the content rather than a full grid. Bounded work (9–10 tiles) keeps layout time flat regardless of feed size. (Originally specced as `binpack2d` Guillotine as in linzer, but its packer unconditionally *rotates* rectangles to fit — sideways selfies — with no way to disable it, and no masonry/justified-layout crate exists for Rust; since all tiles share a width the layout degenerates to simple rows anyway, so a small bespoke shelf packer replaces the dependency.)
* **Caching = stale-while-revalidate, in-memory, keyed by a list signature** (this supersedes a naive per-request recompute):
    * **Cache key** is a normalised signature (hash) derived from the served list's *contents* — the ordered image ids of the tiles that go into the montage — **not** `refreshed_at` (which can move without the montage changing, or vice-versa).
    * **Startup warm-up:** on feed startup, generate once and populate the cache; delay readiness until it completes. A generation error at startup is **non-fatal** — start with an empty cache and continue serving.
    * **Per request:** read the current served list and compute its signature. If the cache holds an entry with the *same* signature → serve it immediately. If the cache is empty or the signature mismatches → trigger a **single-flight** background regeneration and wait up to ~200ms; if it lands in time use the fresh image, otherwise serve the stale entry (or nothing, if empty) and let the regeneration finish in the background. Generation never blocks a request for long, and the list changes rarely, so the hot path is almost always a cache hit.
    * **HTTP caching via ETag, not `last-modified`.** The route sets a strong `ETag` whose value **is the content signature** (the ordered-image-id hash) and honours conditional GET against `If-None-Match` (`304`). This is a better fit than `home()`'s time-based `last-modified`: the montage's identity is its content, so ETag invalidates on *content change* rather than on a clock, and it reuses the signature we already compute for the in-memory cache (one source of truth for "is this the same image"). `web-support` only has `last-modified`/`If-Modified-Since` helpers today, so this adds a small ETag companion (`set_etag` + an `If-None-Match` check) there. A short `cache-control` still rides along so scrapers/CDNs revalidate cheaply on top of the in-memory cache.
* **Meta tags** added to `home.html` `<head>`: `og:image` (absolute URL to the preview route), `og:image:width`/`og:image:height` = 1200/630, `og:title`/`og:description`/`og:url`/`og:type`, and `twitter:card = summary_large_image` + `twitter:image`. Absolute URLs are built from the configured site base URL (the same value already used for the QR code / site URL).
* **Degenerate cases:** fewer than the target count → compose with whatever live tiles exist. **Zero** usable tiles → serve a static branded fallback PNG (committed asset) rather than 404, so the `og:image` meta tag always resolves to a real image.
* **New dependency:** none for layout (the shelf packer is a few lines of bespoke code — see the Layout decision). `image` (0.25, png+jpeg) is already a workspace dependency; add it to `skeet-feed`.

### Tasks

Built as a walking skeleton — keep it compiling and end-to-end at each step, TDD where there's a pure function to pin.

* [x] **Route + meta-tag skeleton (end-to-end first).** Add the preview route to `skeet-feed` serving a **placeholder/static** 1200×630 PNG, and wire the `og:*` / `twitter:*` meta tags in `home.html` `<head>` pointing at it (absolute URLs from the site base URL). Verifies the OG plumbing (route reachable, correct `content-type`, tags present, image unfurls) before any composition exists.
* [x] **Montage composition as a pure function.** `compose(tiles: &[DynamicImage], now/size) -> Vec<u8>` (PNG bytes): pack the tiles into a 1200×630 canvas via `binpack2d` Guillotine (add the dep + `image` to `skeet-feed`), apply the bottom fade, encode PNG. Unit-test it against small synthetic input images (asserts output dimensions, PNG magic bytes, deterministic for fixed input, handles < target count). No network or web framework in this test. *(Layout done as bespoke shelf rows, not `binpack2d` — see the Layout decision for why.)*
* [x] **Tile selection + signature.** From `published_images()`, filter `is_live`, take the first 9–10, and derive the normalised content signature (hash of the ordered image ids used). Unit-test: same list → same signature; reordered/changed tiles → different signature; `is_live` filtering excludes dead items.
* [ ] **Tile fetching + `moka` image cache.** Download the selected tiles' CDN thumbnails (bounded concurrency) via the existing `reqwest` dep and decode them to `DynamicImage`, going through a bounded `moka::future::Cache<ImageUrl, DynamicImage>` (add the `moka` dep) so a URL is fetched+decoded at most once while cached. A fetch/decode failure for one tile degrades gracefully (skip it / compose from the rest) rather than failing the whole image, and must not poison the cache (don't cache failures).
* [ ] **Stale-while-revalidate cache.** In-memory cache keyed by the signature with **single-flight** background regeneration: per-request lookup, ~200ms wait-for-fresh-then-serve-stale, and non-fatal **startup warm-up**. Test the state machine deterministically (hit on matching signature; miss triggers regen; stale served when regen is slow; empty-cache path).
* [ ] **ETag caching.** Add a small ETag companion to `web-support` (`set_etag` + an `If-None-Match` check, unit-tested there alongside the existing `last-modified` helpers). On the route, set the `ETag` to the content signature, emit a short `cache-control`, and return `304` on a matching `If-None-Match`.
* [ ] **Zero-tile fallback.** Commit a static branded fallback PNG and serve it when there are no usable tiles, so `og:image` always resolves.
* [ ] **Verify + polish.** `just clippy` + `just test-no-docker`; `/verify` the route end-to-end (fetch `/preview.png`, confirm a valid 1200×630 PNG and that a link-preview validator sees the tags). Confirm the fetch/compose path doesn't regress the home page's latency on a warm cache.
